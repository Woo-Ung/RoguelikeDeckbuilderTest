# 프로젝트 계획 규칙

> 개별 업무 Workflow(`WorkflowRules.md`)에 앞서, 여러 업무에 걸친 일정과 방향을 정하는 선택적 사전 단계
>
> 이 단계는 `WorkflowRules.md`의 필수 진입 조건이 아니며, 기존 단계의 진입/종료 조건에 영향을 주지 않는다.

---

## 1. 적용 대상

| 대상 | 예시 |
| --- | --- |
| 새 프로젝트 시작 | 프로젝트를 처음 만들 때 |
| 대규모 기능 추가 | 싱글 게임에 멀티플레이 추가, 스토리 모드만 있던 게임에 무한 모드·타임어택 모드 추가 |

## 2. 진입 조건

- 사용자가 계획을 세워달라고 요청하면 이 단계를 진행한다. (기본 방식)
- 아래에 해당하는 경우, Claude가 프로젝트 계획을 권유한다.
    1. 사용자가 새 프로젝트를 시작한다고 말한 경우
    2. 이슈를 2개 이상으로 나눠야 할 것으로 보이는 작업
    3. 기존 시스템 여러 개의 구조가 바뀌는 작업
- 권유만 하며, 사용자가 거절하면 이 단계를 생략한다.
- 이미 진행 중인 프로젝트의 시작 계획은 사용자가 요청할 때만 작성한다.
- 예시:
    ```markdown
    멀티플레이 추가는 네트워크, 플레이어, UI 등 여러 시스템의 구조가 바뀌는 작업이라 프로젝트 계획을 먼저 세우는 것을 권장합니다.
    계획을 작성할까요?
    ```

## 3. 브리핑과의 차이

| 구분 | 프로젝트 계획 | 브리핑 (`WorkflowRules.md`의 `4. 브리핑`) |
| --- | --- | --- |
| 범위 | 여러 업무(이슈)에 걸친 일정과 방향 | 업무 하나의 범위와 작업 순서 |
| 시점 | 개별 Workflow 시작 전 | 각 업무의 착수 명령 후 |
| 결과물 | 계획서 파일 | 응답으로 제시하는 브리핑 |

## 4. 진행 순서

1. 요구사항 확인
    - 프로젝트 목표, 구현 범위, 제약사항을 확인한다.
2. 기존 구조 분석
    - 대규모 기능 추가인 경우, 영향을 받는 기존 코드와 기술 문서를 검토한다.
    - 기존 시스템과의 의존성과 변경 영향을 확인한다.
    - 신규 프로젝트인 경우 생략한다.
3. 개발 계획 수립
    - 주요 시스템과 기능별 구현 방향을 검토한다.
    - 시스템 간 의존성을 고려해 개발 단계와 작업 순서를 정한다.
    - 구현 방식이 여러 가지인 경우, 장단점과 추천안을 제시한다.
4. 예상 일정 산정
    - 단계별 중요도와 난이도를 평가한다.
    - 1인 개발, 하루 6시간 기준으로 예상 소요 시간과 전체 개발 기간을 산정한다.
    - 산정한 일정은 실제와 다를 수 있는 예상치임을 계획서에 표시한다.
5. 계획서 작성
    - 계획서 파일은 사용자가 계획서 작성을 요청한 경우에만 생성한다. 권유에 대한 사용자의 동의도 작성 요청으로 본다.
    - 작성 요청이 없으면 1~4단계 결과를 응답으로만 제시한다.
    - `5. 산출물`의 양식으로 계획서 초안을 작성해 저장 위치에 파일로 저장한다.
6. 사용자 승인
    - 저장한 계획서 초안을 검토하도록 안내하고 승인을 요청한다.
    - 사용자가 수정을 요청하면, 수정 내용을 제시하고 파일 수정 승인을 받은 뒤 반영하고, 다시 계획서 승인을 요청한다.

## 5. 산출물

- 양식 : `Docs\Template\Plan Template.md`
- 저장 위치 : `Docs\Plan\[계획명] Plan.md`
- 계획서는 나중에 참고하는 자료이며, 규칙 문서가 아니다.
    - 계획서와 규칙 문서(`TechSpec.md`, `Docs\Claude\Code\` 등)의 내용이 다르면 규칙 문서를 따르고, 그 차이를 사용자에게 보고한다.

**종료 조건** : 계획서에 대한 사용자의 승인, 작성 요청이 없는 경우 1~4단계 결과의 응답 제시, 또는 사용자의 생략 결정

## 6. 이후 연결

- 계획에 포함된 각 작업은 `WorkflowRules.md`의 `1. 업무 유형 분류`부터 개별 업무로 진행한다.
- 개별 업무의 브리핑 내용이 계획서와 다르면, 그 차이를 브리핑에 명시한다.
