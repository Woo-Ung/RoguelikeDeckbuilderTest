# Plan 작성 규칙

> 프로젝트 규칙을 작성할 때의 규칙.
>
> Plan 작성 양식은 `@Docs\Template\Plan Template.md`를 참고.
>
> 해당 문서는 각 섹션에 대한 작성 규칙을 정의한다.

## 1. Title

- 계획의 핵심 내용을 나타내는 제목으로 작성한다.
- 신규 프로젝트는 프로젝트명, 대규모 기능 추가는 핵심 변경 사항을 기준으로 작성한다.
- 세부 구현 내용이 아닌 프로젝트 또는 시스템 단위로 작성한다.

## 2. 계획 개요

- 계획의 목적과 전체 작업 범위를 기재한다.
- 리스트 형식으로 작성하며, 불필요한 표현을 제거해 간결하게 작성한다.
- 아래 항목을 포함한다.
    1. 계획명 : 계획을 식별하는 이름
    2. 계획 유형 : 신규 프로젝트 / 대규모 기능 추가
    3. 목적 : 계획을 수립하는 배경과 달성하려는 목표
    4. 작업 범위 : 계획에 포함되는 주요 시스템 및 기능
- 개별 클래스나 메서드 등 세부 구현 내용은 작성하지 않는다.
- 예시:
    ```markdown
    ## 계획 개요

    - 계획명 : 카드게임 개발
    - 계획 유형 : 신규 프로젝트
    - 목적 :
    - 작업 범위 :
    ```
    ```markdown
     ## 계획 개요
     
    - 계획명 : 대규모 멀티 플레이 개발
    - 계획 유형 : 대규모 기능 추가
    - 목적 :
    - 작업 범위 :
    ```

## 3. 현황 분석 (As-is)

- 대규모 기능 추가 시 기존 프로젝트의 현재 구조와 동작을 분석한다.
- 변경 대상 시스템과 관련 기능을 기재한다.
- 기존 코드 및 기술 문서에서 확인된 사실을 기준으로 작성한다.
- 신규 프로젝트의 경우 해당 섹션을 생략한다.

- 예시:
    ```markdown
    ## 현황 분석 (As-is)

    - 플레이어 입력 및 이동 처리를 로컬에서 수행
    - 전투 판정과 게임 진행을 단일 GameManager에서 관리
    - 네트워크 연결 및 동기화 시스템 없음
    ```

## 4. 목표 (To-be)

- 계획 완료 후 예상되는 시스템의 동작과 결과를 기재한다.
- 리스트 형식으로 작성하며, 불필요한 표현을 제거해 간결하게 작성한다.
- `2. 계획 개요`의 목적과 중복되지 않도록 구체적인 달성 목표 중심으로 작성한다.
- 구현 방식보다 최종적으로 제공해야 할 기능과 동작 중심으로 작성한다.

- 예시:
    ```markdown
    ## 목표 (To-be)

    - 온라인 2인 멀티플레이 지원
    - 플레이어 간 이동 및 전투 상태 동기화
    - 기존 싱글플레이 기능 유지
    - 로비를 통한 세션 생성 및 참가 지원
    ```

## 5. 시스템 설계

- 목표 달성을 위해 필요한 주요 시스템과 역할을 정리한다.
- 시스템 간 연관 관계 및 의존성을 기재한다.
- 시스템 단위로 작성하며, 개별 메서드 수준의 상세 설계는 지양한다.
- 표 형식으로 작성한다.

- 예시:
    ```markdown
    ## 시스템 설계

    | 시스템 | 주요 역할 | 연관 시스템 | 구현 방향 |
    |---|---|---|---|
    | Network System | 연결 및 세션 관리 | Game System | 네트워크 세션 관리 구조 추가 |
    | Player System | 플레이어 입력 및 상태 관리 | Network System | 로컬/원격 플레이어 제어 분리 |
    | Battle System | 공격 및 피격 판정 | Player System | 전투 결과 동기화 구조 검토 |
    ```

### 기술 및 설계 방향

- 시스템 구현에 필요한 주요 기술과 설계 방식을 기재한다.
- 데이터 관리 방식, 시스템 간 통신 구조 및 필요한 디자인 패턴을 검토한다.
- 복수의 구현 방식이 존재하면 장단점과 추천안을 제시한다.
- 불필요한 추상화나 과도한 확장성을 위한 구조 도입은 지양한다.
 - 사용자 결정이 필요한 사항은 임의로 확정하지 않는다.

- 예시:
    ```markdown
    ### 기술 및 설계 방향

    - 네트워크 라이브러리 : Netcode for GameObjects / Mirror 비교 검토
    - 플레이어 입력 : 로컬 플레이어만 입력을 처리하도록 분리
    - 전투 판정 : 서버 권한 기반 판정 방식 검토
    ```

### 기존 시스템 영향

- 대규모 기능 추가 시 기존 시스템에 미치는 영향을 기재한다.
- 기존 기능의 변경 또는 유지가 필요한 부분을 구분한다.
- 시스템 간 의존성 변경 및 호환성 문제를 검토한다.
- 신규 프로젝트의 경우 해당 섹션을 생략한다.

- 예시:
    ```markdown
    ### 기존 시스템 영향

    - PlayerController : 로컬 및 원격 플레이어 제어 구조 분리 필요
    - GameManager : 싱글플레이와 멀티플레이 진행 방식 분리 검토
    - BattleManager : 네트워크 환경에서 공격 및 피격 판정 처리 방식 변경 검토
    - 기존 싱글플레이 동작 유지 필요
    ```

## 6. 개발 계획

- 전체 작업을 시스템 또는 주요 기능 단위의 개발 단계로 구분한다.
- 시스템 간 의존성과 선행 조건을 고려하여 구현 순서를 결정한다.
- 각 단계의 주요 구현 내용, 중요도 및 난이도를 기재한다.
- 개별 Issue에서 다룰 세부 파일 변경이나 메서드 구현 내용은 지양한다.
- 중요도는 매우 높음 / 높음 / 보통 / 낮음으로 구분한다.
- 난이도는 높음 / 보통 / 낮음으로 구분한다.
- 표 형식으로 작성한다.

- 예시:
    ```markdown
    ## 개발 계획

    | 순서 | 작업 단계 | 주요 구현 내용 | 선행 조건 | 중요도 | 난이도 |
    |---|---|---|---|---|---|
    | 1 | 네트워크 기반 구축 | 연결 및 세션 관리 | 없음 | 매우 높음 | 높음 |
    | 2 | 플레이어 동기화 | 이동 및 상태 동기화 | 1단계 | 매우 높음 | 높음 |
    | 3 | 전투 시스템 연동 | 공격 및 피격 판정 동기화 | 2단계 | 높음 | 높음 |
    | 4 | 로비 UI | 세션 생성 및 참가 UI | 1단계 | 높음 | 보통 |
    | 5 | 통합 테스트 | 멀티플레이 기능 검증 | 1~4단계 | 매우 높음 | 보통 |
    ```

## 7. 예상 일정

- `6. 개발 계획`에서 정의한 작업 단계를 기준으로 예상 일정을 산정한다.
- 하루 6시간 개발을 기준으로 계산한다.
- 구현뿐 아니라 테스트 및 통합 검증에 필요한 시간을 포함한다.
- 단계별 예상 시간과 일수를 표 형식으로 작성한다.
- 전체 예상 개발 기간을 별도로 기재한다.
- 기술적 불확실성이 큰 경우 예상 기간이 변동될 수 있음을 명시한다.

- 예시:
    ```markdown
    ## 예상 일정

    | 작업 단계 | 예상 시간 | 예상 일수 |
    |---|---|---|
    | 네트워크 기반 구축 | 18시간 | 3일 |
    | 플레이어 동기화 | 24시간 | 4일 |
    | 전투 시스템 연동 | 30시간 | 5일 |
    | 로비 UI | 12시간 | 2일 |
    | 통합 테스트 | 18시간 | 3일 |
    | **합계** | **102시간** | **17일** |

    - 전체 예상 기간 : 17일 (하루 6시간 기준)
    ```

## 8. 검증 계획

- 각 개발 단계의 정상 동작 여부를 확인할 검증 항목을 작성한다.
- 개별 Issue의 완료 조건(DoD)과 중복되는 세부 사항은 지양한다.
- 시스템 간 연동 및 전체 기능의 통합 검증을 포함한다.
- 기존 프로젝트의 경우 기존 기능의 정상 동작 유지 여부를 확인한다.
- 체크리스트 형식으로 작성한다.

- 예시:
    ```markdown
    ## 검증 계획

    ### 단계별 검증

    - [ ] 네트워크 세션 생성 및 참가 정상 동작
    - [ ] 플레이어 이동 및 상태 동기화 정상 동작
    - [ ] 네트워크 환경에서 전투 판정 정상 처리

    ### 통합 검증

    - [ ] 두 플레이어 간 게임 시작부터 종료까지 정상 진행
    - [ ] 연결 해제 및 재접속 상황 확인
    - [ ] 기존 싱글플레이 기능 정상 동작
    ```

## 9. 위험 요소 및 미확정 사항

- 예상되는 기술적 문제와 프로젝트 진행에 영향을 주는 위험 요소를 기재한다.
- 위험 요소별 발생 가능 문제와 대응 방안을 함께 작성한다.
- 기술적 불확실성이나 결정되지 않은 설계 방향을 명시한다.
- 사용자 결정이 필요한 사항은 별도 항목으로 구분한다.
- 해당 사항이 없는 경우 섹션을 생략한다.
- 예시:
    ```markdown
    ## 위험 요소 및 미확정 사항

    | 항목 | 내용 | 대응 방안 |
    |---|---|---|
    | 네트워크 지연 | 플레이어 간 위치 차이 발생 가능 | 동기화 및 보간 방식 검토 |
    | 전투 판정 | 클라이언트 간 판정 결과 불일치 가능 | 판정 권한 구조 검토 |
    | 기존 시스템 | 싱글플레이 코드와 충돌 가능 | 기존 기능 회귀 테스트 |
    ```
## 10. 사용자 결정 필요 사항
- 여러가지 방향으로 개발을 할 수 있는 기능의 경우 사용자에게 선택지를 보여줌
- 선택지를 보여주고 추천과 그 이유를 기입
- 예시:
    ```markdown
    - 플레이어의 이동 구현은 어떤 방식을 사용할까요?
        - A. Rigidbody 물리 방식
        - B. Transform 제어 방식
        - C. CharacterController 컴포넌트 방식
        - **중력, 충돌 상호작용이 자연스러운 A방식을 추천합니다.**
    -
    ```
